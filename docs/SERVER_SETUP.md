# MicroMarket Control v0.2.0 — серверный пилот

## Статус
Архив — код и конфигурация, НЕ уже размещённый сайт. Публикации нет.
Целевая среда: Linux, Docker Engine + Compose v2, Python 3.12 в контейнере,
PostgreSQL 16, Nginx. Проверки: VERIFICATION.md. Это Linux-команды, не PowerShell.
Используется одна демо-организация и индивидуальная учётная запись владельца.
Нет публичной регистрации, amoCRM и ИИ пока не подключены.
Перед доступом из интернета повторно проверить зависимости на уязвимости.
До реального учёта устранить/принять ограничения из KNOWN_LIMITATIONS.md.

## Закрытый запуск после выбора сервера
Распакуйте в отдельный каталог, например /opt/micromarket. Старую рабочую
папку и БД не заменяйте. Из каталога с manage.py:

```sh
python3 scripts/init_server.py
sh scripts/dev_certificate.sh
sh scripts/server.sh build
sh scripts/server.sh up -d db
sh scripts/server.sh run --rm web python manage.py migrate --noinput
sh scripts/server.sh run --rm web python manage.py bootstrap_pilot --confirm-demo --username owner
sh scripts/server.sh run --rm web python manage.py check --deploy
sh scripts/server.sh run --rm web python manage.py check_pilot_ready
sh scripts/server.sh up -d web proxy backup
sh scripts/server.sh ps
```

Пароль владельца вводится скрыто дважды: минимум 12 символов, не популярный
и не только цифры. Не передавайте его аргументом команды или в чат.
bootstrap работает ТОЛЬКО на пустой базе; повторный запуск её не перезаписывает.
Сначала bootstrap, затем при необходимости технический администратор:

```sh
sh scripts/server.sh exec web python manage.py createsuperuser
```

Владелец входит через /accounts/login/, технический администратор — /admin/.
demo/demo12345 на сервере НЕ работает. Старые seed-команды заблокированы.
Не импортируйте старую SQLite-базу с демо-администратором.
Перенос реальной БД — отдельная миграция с резервной копией и проверкой.

## Что закрыто
compose.server.yml публикует только 127.0.0.1:8443 — на самом сервере.
PostgreSQL и Gunicorn не имеют опубликованных портов; DB-сеть внутренняя.
Клиент пока не может открыть сайт из интернета. Для проверки на VPS:

```sh
ssh -N -L 8443:127.0.0.1:8443 USER@SERVER
```

Откройте https://localhost:8443. Самоподписанный сертификат вызовет предупреждение
браузера. Это только разработческий тест: не просите клиента отключать защиту
браузера и не передавайте такую ссылку как готовую услугу.

## Перед доступом владельца — отдельное согласованное действие
Нужны домен, доверенный TLS-сертификат, его автоматическое продление,
выбранный режим ограничения доступа. robots.txt и случайная ссылка НЕ защищают
данные. Защита — авторизация, HTTPS и при необходимости VPN/IP-ограничение.

Администратор настраивает:
1. Домен в DJANGO_ALLOWED_HOSTS и https://домен в DJANGO_CSRF_TRUSTED_ORIGINS
   файла .env.server. Пароль БД и SECRET_KEY сохраняет.
2. Доверенные fullchain.pem и privkey.pem в deploy/tls (вне архива).
3. Привязку Nginx к согласованному адресу/порту и firewall. Замена
   127.0.0.1:8443 внешним адресом является публикацией — без подтверждения НЕ делать.
4. Nginx server_name, отклонение неизвестных имён и продление TLS.
5. Копирование резервных копий вне VPS, мониторинг и уведомления о сбоях.
6. Проверки из VERIFICATION.md на целевом сервере.

Только Nginx доступен клиентам. X-Forwarded-Proto перезаписывается прокси.
Нельзя открывать Gunicorn наружу или добавлять прокси без проверки доверия
к заголовкам. Лимит входа Nginx — 5 запросов/мин на IP, burst 5; превышение — 429.
Сотрудники за одним IP делят лимит. Для масштаба нужны дополнительные ограничения
по аккаунтам и настройка trusted proxies.

## Ежедневная работа
```sh
sh scripts/server.sh logs --tail=100 web proxy backup
sh scripts/server.sh exec web python manage.py check_pilot_ready
sh scripts/server.sh exec web python manage.py clearsessions
sh scripts/server.sh restart web
```

После restart проверить вход, данные и контейнеры.
Миграции — отдельный шаг выпуска; статика собирается при старте web.
Данные хранятся в pgdata volume. НЕ выполнять docker compose down -v: удалит БД.
Секреты — в .env.server, не в шаблоне .env.server.example.
init_server.py не перезаписывает существующий .env.server.
Сохраните защищённую резервную копию этого файла отдельно от исходников.
Обычный docker-compose.yml — прежний ЛОКАЛЬНЫЙ режим, не серверный!

## Резервные копии
backup делает pg_dump при старте и каждые 24 часа. Готовый .dump появляется после
проверки формата. При сбое контейнер перезапускается; healthcheck проверяет свежесть.
Уведомления администратору пока не подключены.
Автоматического удаления старых копий НЕТ: контролируйте место и согласуйте срок
хранения. Копии на том же VPS не защищают от его утраты.
Дамп содержит данные и хеши паролей, храните его с ограниченным доступом.

```sh
sh scripts/server.sh run --rm backup /bin/sh /opt/backup.sh once
sh scripts/verify_restore.sh backups/ТОЧНОЕ_ИМЯ.dump
```

verify_restore создаёт НОВУЮ временную БД, восстанавливает дамп одной транзакцией,
проверяет таблицу продаж и удаляет только созданную временную БД. Рабочую не меняет.
Это не заменяет сверку всех показателей на отдельном восстановленном стенде.

Аварийное восстановление рабочей БД выполняет администратор после согласования:
остановить web/proxy/backup, сохранить аварийную копию, восстановить проверенный
дамп в новую БД, проверить миграции и суммы, переключить конфигурацию и запустить.
Не выполнять pg_restore --clean на рабочей БД без отдельного согласования.

## Обновления
Секреты и pgdata не заменять. До миграций — копия и проверка восстановления.
Сборка -> миграции -> check --deploy -> запуск -> приёмка.
Откат кода требует совместимости со схемой БД. В v0.2.0 новых миграций нет.
Автоматического переноса SQLite в PostgreSQL нет.
